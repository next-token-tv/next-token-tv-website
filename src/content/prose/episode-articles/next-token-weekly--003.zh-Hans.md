一个模型不写文章、不陪人聊天，只返回一个选择、一个分数，或者一个“是”与“否”，还能用来做什么？Jev 把这个问题摆到了开发者面前。与追求更长回答、更复杂推理的模型不同，它让人重新考虑：程序中的哪些判断，其实不需要一整段语言。

本期的另一个热点，则是个很具体的使用烦恼：用 Agent，怎么还用出了买带鱼屏的需求？浏览器、聊天区、任务列表一起挤进窗口，原本够用的显示面积突然变得局促。先看 Jev 的尝试与边界，再看这笔意料之外的屏幕账。

## Jev：把模型放进判断环节

[Jev](/wiki/products/jev) 的输出不是一段解释，而是可以交给程序继续处理的结果。选择、评分、是非判断，覆盖了不少看似简单、却很难只靠固定规则解决的任务。

比如，从三百多条记忆中筛出值得保留的信息。一次节目中分享的试用，让 Jev 给这些记忆打分，结果整理出约十八条比较重要的内容。试用者观察到，它更偏好抽象信息，而不是零碎琐事。这还不是严格的效果评测，但它说明了一种用法：要的不是模型写出一篇总结，而是替后续处理完成一次筛选。

另一个尝试是给约一万名微信好友打标签。输入是聊天记录和共同群组，候选标签有二十多个，一个人可能同时符合多项。任务因此被拆成一连串独立的是非题：是否符合这个标签，再判断是否符合下一个标签，而不是要求模型一次返回所有标签。

这样的拆分，让原本串在一起的判断有了并行处理的可能。每天的聊天记录也可以用相近的方法扫描，筛出待办事项和重要信息。录制时，这些任务仍在运行，与其他小模型的对照测试也尚未完成；初步体验不能代替最终的准确率数据。

“快”到底能带来多少收益，还取决于它被放在什么位置。如果一个环节只占总工作量的 1%，即使把它优化 90%，整体改善也只有 0.9%。海量、高频的判断任务，比偶尔调用一次的小功能，更能检验这类模型的价值。

## 能稳定返回答案，不代表答案正确

Jev 的新鲜感容易让人忙着寻找用法，但实际使用还有一道不能跳过的门槛：它做出的判断，究竟准不准？

格式可靠和内容正确，是两回事。语言模型被要求输出 JSON 时，仍可能返回不符合要求的格式，程序需要为此补上重试与保护逻辑。稳定的结构化输出可以减少这部分工程负担，却不能证明某个分类、分数或选择就是正确答案。

节目中转述的模型文档还列出了多跳推理、复杂指代、计算与日期处理等限制，无关上下文也可能影响准确率。不能因为结果简短、返回迅速，就把这些困难视为已经解决。

把它理解成一个 **smart if else**，比把它想成包办一切的智能体更贴近这里的用法。通用模型理解任务、规划步骤，小模型承担部分判断，确定性的计算继续交给程序。它值得尝试的地方，是那些规则难以写全、又需要反复执行的判断环节；是否值得替换原有方案，仍要靠具体任务的测试回答。

## 通用模型变强，专用工具会消失吗？

模型的分工也出现在多模态和创作工具的话题里。音频、视频分别都有模型，为什么还需要放在一起理解？一段故事片就是很直观的例子：声音、画面和转场共同构成表达，先各自转成文字标签，再交给另一个模型，未必还保留着原来的关系。

专用能力的另一个问题是入口。[Arrow](/wiki/products/arrow) 的 SVG 生成能力可以服务图标、设计素材和印刷，但用户未必愿意为每项能力单独配置一个模型。如果已有 Agent 能把它当工具调用，使用门槛就可能不同。

而代码生成又提供了另一条路径。一次软件宣传视频的制作中，配乐起初被以为来自素材网站，追问后才发现是用代码制作的。类似地，模型也能通过 [Blender](/wiki/products/blender) 生成画面。专门训练一个模型，和让通用模型调用程序完成任务，未必总是截然分开的两种选择。

但这是否意味着专用模型会被替代，仍有分歧。一种判断是，通用智能会逐步覆盖更多专门能力；另一种判断是，现阶段各类模型仍有各自优势。能用代码做出一个结果，不等于所有相关需求都已被满足。

## 用 Agent，还得买带鱼屏？

买带鱼屏的念头，来自 [Codex](/wiki/products/codex) 内置浏览器的实际使用。

过去，一块屏幕可以主要留给网页。浏览器进入 Agent 界面之后，旁边还要放会话列表和聊天区。网页没有变窄的理由，新增的界面却需要空间。如果希望保留原来的网页显示宽度，再把这些区域放在旁边，更宽的屏幕就成了一个自然的念头。

这不是使用 Agent 的硬件门槛，而是一种具体布局下的体验：屏幕同时容纳的内容变多了，普通宽高比下的分屏开始难安排。需要看着网页，又需要与 Agent 对话，两个区域很难始终只留一个。

不过，窗口更宽也不能解决所有问题。链接究竟在侧栏打开，还是弹出独立窗口，同样影响使用。一次点击之后，内容应该出现在哪里，最好是可预期的；如果窗口反复变换位置，空出来的显示面积也未必好用。

项目和浏览器标签页的关系，则是另一个尚待理顺的问题。同一份工作涉及的网页，能否跟随项目集中起来，而不是散落在不同会话中？这比单纯多开几个标签页，更接近实际工作中的需求。

“浏览器里加入 Agent”与“Agent 里加入浏览器”，也由此呈现出两种不同的产品路线。前者从浏览习惯出发，后者从任务出发。节目里有对后者更乐观的判断，但它仍是一种产品方向的选择，不能据此认定哪条路线已经胜出。

## 屏幕之外，硬盘也开始不够用

与屏幕空间并列的另一个烦恼，是存储空间。

节目中有一段很具体的个人经历：原本觉得 512 GB 足够，开始大量 Vibe Coding 后却需要经常清理；换成 2 TB 的电脑，约三个月又用掉了 1 TB。这不是所有人的用量标准，却很能说明开发和创作过程中，文件是如何一点点堆起来的。

占空间的也不全是 AI 生成内容。开发依赖、多个工作副本、浏览器缓存、虚拟机、测试系统镜像都可能积累；视频创作者还要保存体积很大的原始素材。清理缓存、增加外部存储、使用 NAS 和备份，是不同层面的问题，不能只靠扩大一次硬盘容量就全部解决。

云端冷存储还带来一个取舍：是否愿意用较长的取回时间，换取更便宜的保存成本？有人可以接受，有人会觉得等待不可忍受。很少访问的归档和随时要用的工作文件，本来就不一定适合放在同一种存储里。

## 能力越多，用户要先做的选择越多？

[ZCode](/wiki/products/zcode) 的 Coding 与 Office 模式，以及 [Claude Code](/wiki/products/claude-code) 的项目、会话与云端工作方式，让另一个产品问题浮了出来：工具覆盖的任务越多，是否就必须增加更多入口？

编程和办公当然有差别，但这种差别是否需要在开始工作之前，先由用户判断一次？如果用户只是想完成一件事，却要先理解 Work、Code、项目和会话之间的关系，选择入口本身就成了额外的任务。

一种更直接的期待是：用户描述要做什么，工具再决定如何完成，而不是要求用户先把任务归入正确的类别。这里的问题不在于功能是否应该区分，而在于多少内部区分有必要暴露在界面上。

## 制作更容易之后，作品仍要找到观众

内容创作里，一个人过去可能既要有想象力，又要会写本子、做视频和剪辑。AI 能帮助完成其中一些步骤，让原来难以实现的表达有了制作出来的机会。

但制作能力提高，不会自动增加观众的时间。作品更容易完成，注意力却仍然有限。想做什么、为什么值得被看见，以及如何让作品真正到达观众面前，依旧是创作者需要回答的问题。

对于创作者，这既是机会，也是新的要求：技术门槛降低之后，不能只停在“已经做出来了”。表达是否成立、作品是否找到受众，仍然要由具体结果检验。
