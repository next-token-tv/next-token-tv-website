一部旗舰手机可以流畅运行大型游戏，性能与电脑的差距一年比一年小。但让 Agent 在手机上干活，情形完全不同：一条命令都执行不了，文件访问不了，工具调不动。算力在涨，可操作性没有跟着涨。

## 电脑上的 Agent 靠什么工作

Agent 在电脑上的能力，建立在几十年积累的基础设施上：文件系统、命令行、[FFmpeg](/wiki/products/ffmpeg)、Git、Bash。一个具体的场景是：装完一个全新的 [Linux](/wiki/products/linux) 发行版，网络没配好，各种配置无从下手，把 [ZCode](/wiki/products/zcode) 装上之后全部交给它操作；有的系统甚至专门写了命令行工具，替 Agent 划定哪些地方能改、哪些不能改，界面崩了、黑屏了，Agent 都能自己修复。

工具链还把产出延伸到代码之外。宣传视频的配乐可以是用 Python 和 MIDI 写出来的，跟着视频节奏走，听不出是程序生成的；借助 Blender 之类的工具，3D 建模和渲染也在同一个可执行的体系里。这些能力有一个共同前提：Agent 能在系统里执行东西。

## 沙盒挡住了同一套能力

同一套东西在手机上跑不了。Node 和常用的脚手架、组件，在 [iOS](/wiki/products/ios) 和 [Android](/wiki/products/android) 的应用沙盒里一个都跑不了；Android 的 ADB 等调试通道近年来也管得越来越严。结果是性能过剩的手机上，Agent 访问不了任何东西——只有端侧模型也没有用，模型在本地，手脚被捆住。

一个具体的故障说明了缺口有多小。一个用来替代运动应用、记录骑行并播报公里数的小软件，在电脑上一天半天就开发完了，拿到手机上测试才发现没有申请定位权限，全程记录下来的都是零速度。问题不是算力，也不难解决——如果能直接在手机上调试，改一行加个权限申请就行。难的不是技术，是手机没有给开发者留下这样做的位置。

同样的反差出现在交互方式上。通过语音操作电脑的场景正在变多，实时语音模型密集发布；而在手机上，这类交互基本被限制在单个应用内部——操作系统不给更深的入口，语音再多也只在应用里打转。

## 上下文也留在电脑一侧

除了执行能力，上下文同样偏向电脑。个人 Memory 可以就是文件系统和文档，挂载一块自己的存储就能自动同步，不必依赖第三方服务；多模态的图像和视频也有地方放。而手机上的信息被锁在一个个应用里，连从云端下载一个文件，找到它都费劲。

于是现实的分工变成了：执行环境放在电脑或者自己掌控的机器上。有人把买来的多套 Coding Plan 装进一台树莓派的虚拟机里，让 Agent 们自己调度、互相补位，定时任务、整理信息、审 PR 都在那台小机器上跑。手机在这一轮分工里，更多是发指令的一端，而不是干活的一端。

## 系统画出的框，和框上的缝隙

在这些限制下，今天的可行路径都在系统允许的范围内，各有代价：

云端执行是把重活放出去的自然选择，省电也省本地资源，但总有需要与本机信息交互的部分留在手机上，而那正是最难的部分。

厂商自己的通道是特权路径。手机厂商可以用系统级能力把手机上的助手连到电脑，跨设备操作，甚至读到应用里的收藏和相册。这是系统内通道，普通开发者拿不到同等的权限。

解除系统保护确实能放开更多，但代价明确：Root 或解锁之后应用可以检测到，银行类应用直接不可用；开发者模式下的调试接口防范较松，那只是现状，不是可以推广的方案。把"解锁"当成通用解法，风险由用户独自承担。

社区也在找系统留下的缝隙。一个方向是借 iOS 自带的浏览器组件——它是系统组件，权限比普通应用宽——来执行 Node.js 和命令行；另一个方向是从 .swift 文件直接在本地编译、渲染出界面，AI 写一个文件，确认之后应用就跑起来。这两个说法目前都停留在演示和讨论层面，库能否上架、稳定性如何，都还需要工程核验。它们被提及的价值在于指出了问题的性质：限制来自系统策略，不是技术做不到。

## 算力已就位，环境没跟上

手机与电脑在 Agent 时代的差距，已经不在芯片上。文件、命令、权限模型，这套让 Agent 得以工作的东西，手机要么没有，要么不给。一个骑行软件的故障说明缺口可能只差一次权限申请，厂商通道说明钥匙握在系统手里，社区库说明缝隙存在但未经检验。算力已经就位，剩下的问题是软件环境什么时候跟上——那决定了手机究竟是 Agent 的遥控器，还是它的工作站。
