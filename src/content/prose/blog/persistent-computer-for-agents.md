给 Agent 交代一个任务，第二天回来接着用：它昨天装的软件还在吗？登录过的账号还有效吗？生成的文件放在哪里？这些问题的答案，取决于它运行在一个临时沙箱里，还是一台不下线的电脑上。

## 任务结束后还剩下什么

最常见的执行环境是临时沙箱：每次对话拉起一个虚拟机，不同对话、不同进程拉起的可能是不同的机器。任务一结束，环境就被回收，装进去的东西和中间状态都不保留。这类做法成本低，代价是上下文没有持久化，任务之间无法积累。

不是所有产品都把执行环境留给用户。一些垂类 Agent 干脆不提供运行代码的能力：参考图传得上去，却调不出来，文件系统形同虚设。问题不在模型没有编码能力，而在于产品没有给它一个能操作的环境。也有产品出现过更极端的情况：环境里的内容直接丢失，用户来不及保存任何东西。

在这样的背景下，持久环境的主张显得很直接：给 Agent 的那台电脑应该一直在，用的时候要能承诺数据不会丢。这一步已经不只是功能差异，而是被当成了产品本身——[Grok Bot](/wiki/products/grok-bot) 把这台"云电脑"作为一个有名字的部件放在台面上，而另一些产品里，同样的东西藏在多层入口背后，用户未必意识到自己已经有一台。

## 沙箱与常驻电脑，是两代产品

Agent 的执行环境这几年走了三步：从只能对话，到能运行一段代码，再到拥有一台自己的电脑——可以装软件、打开网站、用用户的账号登录去操作。前两步里环境是附属品，第三步里环境成了产品的一部分，厂商的思路也随之从"帮你完成一次任务"变成"替你管着一台机器"。

常驻电脑与临时沙箱的差异，在使用中会具体到细节：环境从任务开始到结束一直保持运行，装好的 Skill、登录过的账号状态都还在，下次进来接着用；临时环境每次拉起都是另一个进程，之前的上下文无处可寻。[Manus](/wiki/products/manus) 早期的做法是每个任务分配一台电脑，任务结束即回收——环境有了，持久没有。这两种体验之间隔的不是参数，而是"这台电脑是不是它的"。

不过，"持久"并非所有产品的默认承诺。同为云端环境，[Dots](/wiki/products/dots) 的沙箱更严格：无法 SSH 连接、不允许安装第三方软件，还会频繁重启、重新分配；重启之后写入的内容是否完好，取决于各家实现，需要按版本逐一确认。选择把工作和数据放进哪种环境，持久性是需要单独验证的属性，不是品类固有的保证。

## 有了不下线的电脑，才有了新的任务类型

临时沙箱适合"跑一次"：给一个任务，等一个结果。不下线的电脑打开的是另一类任务——需要一直在场、按日程执行的工作。

一个被转述的用例来自一位做 Mac 清理软件的独立开发者：他把多平台的营销推广交给一台常驻的 Agent 电脑，定时访问欧美的小众论坛，让 Agent 判断每个论坛的调性——有的喜欢独立开发者讲故事，有的偏好知识性干货——再结合大家浏览的时间段发帖，他只需要提供内容。这类任务的关键不是某一次操作多聪明，而是环境可以一直挂着，定时触发、持续观察。

需要登录态的任务同样依赖持久环境。让 Agent 保持一组账号的登录状态，打开浏览器逐个试用一批产品并记录结果，前提都是这台电脑第二天还是昨天那一台。沙箱做不到，因为每次醒来都是陌生的。

## 成本：免费送不起的一代

常驻环境贵在时间。临时沙箱用完即毁，云电脑却要一直开着，成本结构因此完全不同：有的产品不设免费额度，进来就要付费，因为起一台虚拟机就是实打实的开销；也有公司以巨大的资源投入，为海量用户同时提供虚拟机和高额的模型用量，把这笔账算成长期入口的投资——[Muse](/wiki/products/muse-agent) 是后一种，而它显然不是所有厂商都能复制的。

成本的差异也开始反映到产品分层上：有没有电脑、电脑是否持久，正在成为 Agent 产品定价与定位的依据之一。开放程度同样在分化——有的产品允许用户在手机上浏览云端虚拟机的完整文件列表、把单个文件下载下来，有的则把权限收得很紧。评估这类产品时，环境归谁控制、文件能不能拿出来，与它跑任务的能力同样重要。

硬件路线也在分化。除了 Linux 虚拟机，出现了用 Mac 整机提供服务的方式：厂商购置一批 Mac Mini，把 macOS 环境连同远程桌面一起接入 Agent。租用 Mac 环境本是一门老生意，如今被接进了 Agent 的执行层。

## 从一台云电脑到一组电脑

持久环境的第一阶段是一台云电脑：把常用的命令行工具和脚本克隆进去，人在外面用一句话让它查信源、做图、发内容，不必为连回家里那台常驻机专门搭一套通道。第二阶段正在出现：Agent 开始登记和管理多台机器——一台云端电脑之外，再加一台家里常开的 [Mac Studio](/wiki/products/mac-studio)，任务可以落到其中任何一台上。

再往前，是管理一组机器。产品方的规划里已经出现让 Agent 管理整个公司、整个家庭的电脑的想法——这是规划，不是已发布的能力。个人侧的试验也在朝同一方向走：把若干台 VPS 的登录信息交给 Agent 统一管理，让它记录每台机器上跑着什么服务、重启挂掉的服务、在多台机器之间做容灾，相当于多了一个随叫随到的运维工程师。

这条路径的尽头也埋着新的问题。把冷备份交给 Agent 处理之后，备份落在哪个目录、出事时能不能恢复，交托的人未必清楚；管理权交出去越多，对环境的了解就可能越少。给 Agent 一台不下线的电脑，回答的是"任务结束还留下什么"；接下来的问题是，留下的这些东西，谁来清点、谁来负责。
