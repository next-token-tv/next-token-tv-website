网页占一块 16:9 的区域，旁边再放下聊天和会话列表。这是一个很具体的工作界面设想，也足以让人开始考虑一块 5K 带鱼屏。

需求来自 [Codex](/wiki/products/codex) 内置浏览器的使用：网页仍然需要足够的显示宽度，对话也需要留在眼前。当浏览器和 Agent 共用一个窗口，过去主要留给网页的空间，就要重新分配。

屏幕变宽，确实可以把这些区域同时摆出来。但工作界面是否顺手，还取决于窗口会在哪里出现，以及眼前这些网页如何与正在做的事情关联。

## 网页和对话开始争夺空间

独立使用浏览器时，网页可以占据大部分窗口。加入聊天区和会话列表后，如果希望保持原来的网页宽度，就需要在两侧增加空间；如果总宽度不变，就得压缩其中一个区域。

在这样的布局里，宽屏有了很明确的用途：一边查看网页，一边与 Agent 对话，减少反复切换。这解释了为什么使用软件的变化，会引出购买显示器的念头。

不过，把所有区域一直摊开，也会让界面显得拥挤。相关使用反馈中，既有想增加屏幕宽度的需求，也有对区域占地方、窗口反复拆合的不满。它们反映的是同一个界面在不同使用方式下的取舍。

对于需要同时查看网页和对话的工作，更多横向空间可能有用；如果工作过程中频繁改变窗口组合，宽度就只是其中一个因素。

## 窗口出现的位置，需要可以预期

比空间不足更打断操作的，是点击之后不知道网页会出现在哪里。

这次体验中出现过两种情况：网页有时进入侧边浏览器，有时又弹出独立窗口。合并与拆开的状态也会变化。用户既要处理页面上的内容，又要重新寻找窗口、理解它与当前会话的关系。

这种问题不会随着屏幕变宽自动消失。带鱼屏可以容纳更多区域，窗口行为仍然需要稳定。每次操作的结果能够被预期，空出来的空间才容易被利用。

因此，评估这样的界面，除了看能否同时摆下网页和聊天，还要看打开链接、切换页面时，工作能否顺畅地接着进行。

## 标签页应该跟着哪一项工作走

浏览器进入 Agent 后，标签页与项目之间的关系也值得重新考虑。

如果一项工作已经有自己的项目和会话，相关网页却仍然散落在另一套标签页列表里，用户就需要自己维持两者之间的联系。把浏览器放进同一个应用，只完成了界面上的靠近。

更进一步的设想是，让标签页与项目联动：切换到某项工作时，相关对话和网页能够作为一组内容被找到。项目提供组织方式，标签页保留实际页面，两者共同组成这项工作的上下文。

这里讨论的是一种工作空间设计，而非当时已经具备的完整功能。它的价值在于减少两套管理方式之间的割裂，让网页跟随任务组织，而不只是多占一个可见区域。

这与增加屏幕宽度可以同时发生。宽屏让更多内容同时可见，项目联动让这些内容彼此有关。空间和组织方式都到位，浏览器与 Agent 才更容易形成连贯的使用体验。

## 从浏览网页，到围绕任务组织网页

浏览器加入 AI 助手，与 Agent 加入浏览器，有不同的出发点。

前者从既有的浏览习惯出发，在网页旁增加提问或辅助操作的入口；后者从任务和对话出发，把网页作为完成工作时可以打开、查看和操作的内容。

两条路线都可能把网页与聊天放在一起，但界面的组织重心有所不同。对于以任务为中心的使用方式，项目、会话和标签页能否协同，比单独增加一个聊天面板更值得关注。

独立浏览器也仍有自己的使用场景。看视频、刷信息流、阅读文章，并不都需要先建立一个任务。任务中的网页操作，与日常内容消费，可以保留不同的入口。

带鱼屏的念头因此提供了一个具体的观察角度：Agent 的能力进入日常使用后，连屏幕上应该摆什么、放在哪里，都开始发生变化。网页、对话和任务可以共处一屏，接下来的产品问题是，如何让它们也属于同一份工作。
