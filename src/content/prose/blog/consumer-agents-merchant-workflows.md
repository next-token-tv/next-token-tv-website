帮一个人安排生活，听起来是 Agent 很自然的用途。可当任务涉及购买、预约、账户和售后时，一句自然语言背后很快就连着多个系统。模型知道应该做什么，只是开始；它还需要能够读取信息、发起操作，并确认结果。

门店经营则提供了另一种起点。订单、评价、营销活动这些事情每天发生，经营者知道哪里费时间，也更容易指出一份报告是否漏掉了问题。第 006 期对个人助理的讨论，最终转向了美团等平台的商家工具。这个转向值得解释，但不能直接推出国内只有商家 Agent 能成立。

## 商家任务自带一部分上下文

一个陌生的个人用户说帮我安排明天，系统可能还不知道他的工作时间、家庭分工、预算与偏好。相比之下，门店经营任务可以从较窄的问题开始：汇总昨日评价，找出重复出现的投诉，列出需要店长查看的订单异常。

范围较窄并不意味着技术上一定简单，而是业务对象更容易指认。哪家店、哪段时间、哪一组数据、交给谁看，往往可以在现有工作流程中找到答案。用户也能用已有经验判断结果是否相关。

美团官网刊载的 CatPaw 介绍，把数据汇总、异常识别和经营建议列为商家场景，并强调价格等关键决定仍由经营者作出。这是平台对产品用途的说明，不是独立测得的收益数据。它展示了一种务实的边界：先把分散信息整理到经营者可以判断的程度。

## 接近业务，不等于自动拥有权限

平台服务过大量商家，可以积累对业务流程的理解；某个 Agent 能否使用某家店的数据，仍取决于实际授权和接入。不能因为属于同一个生态，就假设所有账户、订单与操作都能随意调用。

可以用三个问题检查一个落地方案。它能看到完成任务所需的数据吗？它有执行相应操作的入口吗？操作后能否查到结果？这三个问题分别对应信息、动作和反馈，缺少任何一项，都可能停留在给建议的层面。

假设系统能分析差评，却不能修改商品说明，它仍可作为经营助手发挥作用，只是交付物应当是待处理事项，而不能宣称已经改善了商品页面。能力范围说得准确，才便于人接手剩余工作。

这个判断也适用于个人助理。获取旅行建议与完成一笔可查询的预订，是不同的服务深度。模型能力相近的两个产品，可能因为可用接口不同，表现出完全不同的实际用途。

## 消费者服务提供了反例

阿里巴巴对千问 App 的官方介绍，明确列出了通过淘宝即时零售下单，并在对话中完成支付的消费者场景。无论具体体验是否稳定，这至少说明个人消费任务也在产品的落地范围内，不能把它们概括为没有用武之地。

值得注意的是这些能力接入了已有的商品、交易与支付系统。它们与商家工具共享的条件，是能把意图交给实际业务处理。用户身份一端是消费者，另一端是经营者，并不改变这个基本要求。

因此，比国内外或个人与商家的简单二分更值得研究的，是服务可以深入到哪里。一个平台可以先覆盖自身能提供完整操作路径的任务，独立助理则需要通过授权接口、合作或界面操作接入更多服务。各条路径的成本与可靠性，需要放到具体任务里比较。

## 商业价值更清楚，也更容易被追问

商家场景的吸引力还在于，使用者通常能说出问题造成的损失：重复整理花了多少时间，哪些异常经常漏看，报告出来后谁来处理。这给产品提供了较明确的评估方向。

不过，报告更快并不自动等于经营更好。减少整理时间、改善决策、增加收入是不同层次的结果。若缺少后续记录，最多只能确认前一层，不能把收入变化都归因于 Agent。

个人助理也有类似问题，只是价值未必都以收入衡量。方便、安心或完成原本搁置的事务，都可能成立。商家任务的优势在于边界和反馈往往更明确，并非个人生活不值得服务。

当 Agent 先进入门店或电商后台，可以把它理解为对现有业务条件的利用。真正决定它能走多远的，仍是可获得的信息、可执行的动作，以及结果能否回到使用者手中。
