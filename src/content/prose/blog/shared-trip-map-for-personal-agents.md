出发前一晚，群里已经有了餐厅链接、集合时间和几张地图截图。第二天一早，有人按旧消息去了景点，有人却以为行程已经改到下午。每个人都参与了讨论，并不代表大家看到的是同一份决定。

个人 Agent 加入群体规划后，这个问题会变得更明显。节目中提到，一群人去泰国旅行时，各自的 Instinct 帮忙沟通集合安排和个人偏好。他们还把行程点共同标在一个网页地图上。[关于 Agent 协调的讨论](/weekly/010/transcript#quote-c3f56b43b9e065e260f0)和[共创地图的描述](/weekly/010/transcript#quote-b9aed743257e38a71b3e)记录了两类操作。各自的 Agent 可以带来建议，共用的网页则给了大家一个查行程的地方。

地图能让建议聚到一起，接下来还需要回答：哪些点只是提议，哪些安排已经生效？

## 地图上的点需要状态

一个实用的行程条目可以包含地点、日期、当地时间和状态。**候选**表示有人提出，但同行者尚未决定。**待核实**表示方向大致可行，营业时间、交通或预约等条件还没有确认。**已确认**则表示约定的确认人已经同意，大家可以据此行动。

这些状态不应由地图上有没有图钉来暗示。一个图钉既可能代表想去的地方，也可能代表必须准时抵达的集合点。如果两者看起来一样，地图越丰富，误解也可能越多。列表视图可以把待核实事项集中展示，地图则帮助大家理解地点之间的距离。

## 同一个景点出现两个时间怎么办

假设两位同行者都想去同一座寺庙。一位建议上午九点，另一位建议下午三点，各自的 Agent 都把建议提交到了共享地图。这时系统可以把两个时间保留为同一地点下的候选，并提示冲突，而不是让最后写入的时间悄悄覆盖前一个。

人选定下午三点后，条目才变成已确认，并记录确认人和变更来源。若之后有人发现寺庙提前关门，新的时间应重新进入待核实或候选状态，并通知受影响的同行者。历史记录至少要让大家看得出原来是什么、谁提出了修改、谁确认了新安排。

时间也要带上时区。如果约在曼谷当地时间下午三点，地图和提醒都写明这一点。导出数据也应保留时区，方便身处不同地方的同行者使用。

## 分享决定，少分享对话

规划可能涉及健康状况、预算或住宿位置。共享地图通常只需要显示与小组决定有关的信息，例如“需要无障碍入口”，而不需要把某人向 Agent 解释身体情况的原始对话一并转发。共享前可让当事人查看将要发布的内容。地图还需要明确谁能看、谁能编辑，以及怎样撤销访问。

共享地图本身已有成熟的产品模式。Google My Maps 支持私下或公开分享、访问控制，以及 KML/KMZ 和按图层导出 CSV。同行者可以共同维护一个地址，同时导出已经确认的路线供别处使用。

一次多人旅行不必先解决所有 Agent 如何互通。先让每个地点的状态、时间和确认记录清楚可见，即使建议来自不同工具，同行者也能知道下一步该按哪份安排走。
