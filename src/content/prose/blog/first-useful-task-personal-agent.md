一个新的 AI 应用装好，打开是一个输入框。对每天离不开 Agent 的人来说，这无所谓；对大多数人，这是一个问题：第一句话该说什么？Personal Agent 这一轮产品的核心主张，正是把 AI 交到这些人手里——而它能否被用起来，取决于第一件有用的事何时发生。

## 第一件事从哪里来

空白输入框隐含着一个假设：用户知道自己想要什么。实际观察与此相反，相当一部分人打开一个 Chatbot 或 Agent，并不知道该让它干什么。起点因此成为设计对象。

一种做法是列场景。一项录制时的体验里，[Muse](/wiki/products/muse-agent) 用一个页签列出具体的生活难题：信用卡被多扣了钱，能不能让 AI 自动把钱要回来；要办一场聚会，能不能让 AI 把物料采购安排好。每个场景点下去就开始执行，不需要用户先想措辞。这些场景都经过挑选，贴近当地生活的真实痛点，而且偏向生活而非工作。另一种做法是推荐：基于长期记忆，为用户挑选可能感兴趣的内容，在不知道干什么的时候提供一个起点。

两种入口的共同点是把"我能帮你什么"翻译成一个可以立刻点下去的第一步。空白聊天框没有消失，只是不再独自承担开场的责任。

## 生活问题不需要工作台

Personal Agent 之所以能这样简化，与另一条产品线有关：Agent 正在分化。面向生活的产品越来越简单，恨不得进去就能聊；面向程序员和生产力的产品自由度越来越高，插件、模型选择、自定义工作流一应俱全。

这种分化对应着任务性质的差异。生活任务没有项目、没有代码库、没有交付物，用户不需要管理会话，不需要理解上下文窗口，甚至不需要知道背后是哪个模型。生产力工具里的那些自由度，在这里全部是负担。所以 Personal Agent 的交互往往退回对话本身——回到最初聊天即用的形态，把复杂性留在系统内部。

反面例子同样说明问题。一项发布初期被记录的体验里，Dots 被放进一个已经有很多入口的侧边栏，用户分不清它和旁边几个产品的区别，上手反而更难。入口多不等于门槛低；对生活场景来说，每多一个需要理解的概念，就少一个会开始用的用户。这些是录制时的产品状态，各自都会继续演进，不构成对某个产品的定论。

入口的位置也是上手的一部分。一条被记录的产品经验是，用户离不开日常软件里已有的联系人列表——有产品把助手做成微信里的一个"好友"，扫码就能聊，转化成本因此大幅下降；平台内助手遵循同一逻辑，入口就在人们每天打开的应用里，位置本身替用户省去了一次迁移。

## 交出去之后，人要看得见

第一件事开始之后，体验的分水岭在执行过程。常见的两类挫败都与沟通有关：一类是没帮上忙反而添了新问题；一类是复读——把用户的话复述一遍，不给结论，再建议"你可能应该干这个"。后一种尤其消耗耐心，因为它花费的是用户的注意力和时间。

表现较好的产品在执行结构上做了区分。仍是 Muse 的体验：它内部只有两个角色，一个负责与用户沟通和派任务，另一个在后台执行；屏幕一角有一个小区域，持续显示后台正在做什么、哪些事项等待审批。左边对话不断线，右边状态可查，用户才能放心把事情交出去。

请求协助的方式同样关键。有些环节 Agent 做不了，需要用户补一小步——怎么说这句话，决定用户觉得"它在帮我"，还是觉得"它在指挥我"。这一段交互的质量不取决于模型能力，取决于产品设计是否把人的感受当作一等对象。

## 会话留给技术，人称留给用户

用得久了会出现组织问题：每件事都要开一个新会话吗？工具类产品按任务切分会话有其道理，但生活里的对话对象是"一个人"，不是一个文件目录。有产品开始把组织方式从会话转向角色：对着同一个人说话，沟通中产生的上下文由系统自动整理提炼。一个可作类比的事实是微信——它的会话列表从来都是人和群，而不是话题和项目。

不过单一会话并非万能。编程、长期项目这类专业工作，仍然需要自己的工作区和隔离的上下文，塞进同一个对话框只会互相干扰。合理的并存方式是：生活交给一个常在的对话，专业工作交给项目化的工具，两者不必强行统一入口。

## 结尾

从空白聊天框到第一件有用的事，中间隔着三层设计：一个不需要措辞的起点，一段看得见、能纠偏的执行，以及一份不必由用户维护的组织结构。三层都齐了，第二次对话才会发生。上手的定义因此可以改写——不是用户学会了产品，而是产品在最初几分钟里完成了一次闭环。
