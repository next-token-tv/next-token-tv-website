让 Agent 查一项国内产品，它给出几条海外报道，随后表示没有更多信息。换一个搜索入口，却找到了原本缺失的中文材料。答案的差别，可能发生在写答案之前：模型根本没有拿到同一批资料。

第七期的一项实践，是把 DeepSeek 搜索 API 包成 Skill，再接进自己的项目。它带来的直接变化，是能够自行安排关键词扩展、并行搜索和结果汇总。这个切入点值得展开，因为搜索成为接口后，开发者获得的不只是另一个搜索框，也获得了决定信息怎样进入 Agent 的机会。

## 找到页面与读到正文，可以分别安排

DeepSeek 官方文档将 Search 定义为返回结构化网页结果的接口，将 Fetch 定义为读取单个网页、返回 Markdown 内容的接口。两者以 JSON API 提供，采用 API Key 认证。这个接口形式允许应用把检索结果交给自己的处理流程，而不必把整项任务固定在某个聊天界面里。[官方说明](https://api-docs.deepseek.com/guides/search/)支持的是这些接口能力，并没有承诺所有网站都能读取。

这样的分工让成本与质量更容易分别处理。先找到候选页面，筛掉明显无关的结果，再读取最有价值的正文，可以减少无效材料进入上下文。重要页面读取失败时，也能明确记下缺口，而不是把搜索摘要当成全文。

对读者来说，搜索摘要足以判断是否值得点开。对需要做决定的 Agent 来说，摘要里缺少的条件，可能恰好会改变结论。例如一个功能仅适用于某一订阅档位，标题和摘要却未必写出这层限制。

## 多搜几个词，要围绕信息缺口展开

节目提出的做法，是先让模型扩展关键词，再并行搜索。这个思路可以继续细化：扩展的每个词，应该对应一种可能遗漏的信息。

假设要确认一款产品是否支持导出数据，可以分别查产品名与导出功能、官方文档中的格式说明，以及版本更新记录。三组检索在回答不同的问题。把同一句话改写十遍、拿回十组近似结果，则未必增加有效信息。

检索还需要结束条件。若问题是确认一个功能是否已经上线，找到明确的官方说明和对应版本，可能已经足够；若问题是比较长期使用体验，还需要不同场景的实际记录。让搜索一直扩张，容易得到更长的材料堆，却没有更清楚的答案。

可以先用一组真实问题检查接入效果：哪些过去找不到，现在找到了；哪些搜到了页面却读不到正文；哪些结果看似相关，实际指向过时版本。这比仅比较返回了多少条结果，更能说明新接口是否弥补了原来的缺口。

## 结果相互冲突时，汇总不应抹平差别

一篇旧评测说功能不支持，后来更新的官方文档说已经提供。把两句各取一半，会生成一个含糊的答案。需要保留下来的，是时间、版本、适用条件和来源身份。

反过来，官方介绍说支持某项能力，用户反馈却指出特定设备上失败，也未必互相否定。前者说明产品承诺，后者可能揭示适用边界。文章或 Agent 应把这层关系解释清楚，而不是用来源数量投票。

一个可用的汇总结果，应当让重要结论能回到具体页面，最好还能定位支持它的段落。无法读取、日期不明或只有转述的材料，可以作为进一步寻找的线索，但不能在汇总时自动升级为已确认事实。

第七期对中文信息覆盖的评价来自当时的使用体验，没有提供统一题集与对照结果。因此，它足以成为接入和验证的理由，还不足以证明某一个搜索接口在所有中文任务中都最好。

## 搜索预算也需要对应任务价值

关键词越多、读取页面越多，工具调用与后续模型处理就越多。一次调查真正需要的预算，取决于问题有多复杂，以及一个错误结论会带来什么影响。

对私人阅读清单，少量来源可能够用；对准备公开发布的产品比较，关键参数就需要逐项核对。并行可以缩短等待，但不会让重复请求消失，也不会自动提高来源质量。

据此设计搜索流程时，可以先给出问题、所需证据和结束条件，再允许 Agent 自行选择检索路径。搜索 API 扩大了可获得的材料，证据管理则决定这些材料能否支撑一个值得采用的答案。
