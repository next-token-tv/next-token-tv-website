假设一个聊天工具已经能把对话整理成 HTML。团队想让更多人知道这项能力，于是在输入框旁加上“导出网页”按钮。按钮本身也许很快就能做出来，真正的产品问题从它上线之后开始：它在移动端放在哪里？空对话能否点击？生成失败时用户看到什么？旧版本的导出文件还能否打开？

节目里谈到，借助 AI 增加功能变得容易。另一段讨论则提出，HTML 生成能力可以存在，却不一定要为它设置专门按钮。[功能扩展的讨论](/weekly/010/transcript#quote-5cbcf812036a18f78089)和[能力与按钮的区分](/weekly/010/transcript#quote-0f7920320d6a6c0f5c10)指向同一个产品取舍：交付能力的成本，和长期提供一个入口的成本，并不相同。

## 一个入口会改变哪些路径

新增按钮后，团队需要定义它与已有导出、分享、复制操作的关系。如果用户先选中一段内容再点击，导出的是选中部分还是整段对话？如果对话正在生成，按钮应等待、禁用还是导出当前内容？这些决定需要写进界面行为，也需要进入测试。

每增加一条路径，测试组合也会增加：不同设备、内容状态、语言、错误和恢复方式都可能与它相遇。不是所有组合都要穷举，但团队需要判断哪些失败会让用户丢失工作，哪些可以用更简单的规则覆盖。Google SRE 的《Simplicity》区分必要复杂度与偶然复杂度，并提醒维护闲置代码和多余 API 的长期代价。在导出这个例子里，保存文件是用户需求。为同一种导出维护多个行为各异的入口，会增加后续修改的范围。

## 把按钮藏起来，用户还能找到吗

按需发现能力可以减少常驻入口。例如用户说“把这段对话做成网页”时，Agent 生成预览，并在预览旁提供保存操作。首次使用时，示例提示或帮助页也可以说明这一可能性。

但用户无法请求自己完全不知道存在的功能。假设导出是多人协作中的高频交付步骤，或者用户需要在离线前可靠保存结果，显眼的导出入口可能比等待自然语言请求更合适。删除、取消、保存等需要及时找到的操作，也不应只靠用户猜命令。

判断入口是否值得常驻，可以先列出它要服务的任务、用户寻找它的时刻，以及找不到时的后果，再观察搜索帮助、失败反馈和实际使用情况。这些信号应结合理解：低使用量也可能意味着入口难找，不能自动证明需求不存在。

## 从上线时就准备退路

上线前先指定负责人、兼容范围和复查时间。若功能后来不再适合常驻，可以先在真实任务中验证替代路径，再提前告知用户、提供数据导出或迁移方式，并保留合理的过渡期。对生成中的操作提供取消，对已执行的可逆操作提供撤回，能让尝试的代价更低。

界面简洁是一种持续维护的结果。下次准备增加入口时，除了估算制作时间，也把它需要长期解释、测试和退役的成本放进决定里。
