# 火线解读 Jev 新范式；用 Agent 还得买带鱼屏？

一个 AI 只会给分、做选择、回答是或否，是能力太少，还是终于没有多说废话？

Jev 引发的兴趣，恰好卡在这个问题上。习惯了让模型写长回答，再看一个只返回结果的模型，很容易先问它“还能做什么”。但换成开发者的处境，问题可能相反：这一步只需要一个判断，为什么每次都得生成一段话？

## 不聊天，到底有什么用？

先看两个实际尝试。

一个是给三百多条记忆打分，筛选值得保留的信息。初步试用整理出了约十八条重要内容，试用者认为它更偏好抽象信息。这里需要的不是文采，而是取舍。

另一个是给约一万名微信好友打二十多个标签。聊天记录和共同群组提供线索，同一个人可以有多个标签，于是每个标签单独判断一次，返回是或否。

后一种做法尤其值得留意。它没有要求模型完整“理解一个人”，而是把任务压成许多小问题。问题之间不依赖顺序，就可以并行处理。

这是一种与聊天很不一样的模型用法：模型不站在前台回答用户，而是放进程序，承担固定的一步。

## 更快，就值得换吗？

未必。先算它占多少。

一个步骤只占总工作量的 1%，即使把它优化 90%，整体收益也不过 0.9%。如果为了接入新模型，又增加了配置、调用和检查的负担，演示里看起来惊人的速度，在完整任务里未必同样显眼。

所以，海量、高频不是一句装饰。反复执行的判断足够多，单次调用的改善才有机会积累起来。

但还有更难的一问：它判断得对吗？

一万个好友的测试在录制时仍未完成，也没有做完与其他小模型的对照。初步速度不错，是继续测试的理由，不是宣布胜出的理由。

## 都能保证输出了，为什么还会错？

因为保证格式，不是保证事实。

一个合法的 JSON，可以装着错误分类。一个干净的“是”，也可能本来应该是“否”。

结构化输出解决的是程序能不能顺利接住结果，准确率解决的是接住之后该不该相信它。前者减少重试和解析的麻烦，后者仍要靠任务数据验证。

节目中转述的限制，包括复杂指代、多跳推理、计算和日期处理，也提醒使用者不要把输出简单误认成任务简单。

把 Jev 当成 smart if else，反而容易放对位置：规则难写的部分让模型判断，确定性的计算留给程序，复杂的规划由更合适的模型负责。不必因为一个部件好用，就让它接管全部工作。

## 通用模型这么强，还要专用模型吗？

这个问题在配乐案例里变得有意思了。

一次软件宣传视频的配乐，起初被以为是从素材网站找来的，后来才知道是代码制作的。既然通用模型能写代码做配乐，也能通过 Blender 生成画面，专用模型是否迟早会被覆盖？

这里至少有两个不同的判断。

一种看法强调通用能力的扩张：过去要分别解决的事，可能被同一个模型通过工具完成。另一种看法强调结果的差异：能做一次，不代表对各种要求都做得好，专用能力暂时仍有位置。

Arrow 的 SVG 生成便是一个具体例子。图标、设计素材、印刷都有需求，但用户是否需要单独打开一个工具？还是让已有 Agent 调用它就够了？

“能力还有没有价值”和“用户还需不需要一个独立入口”，不能混成同一个问题。

音视频理解也一样。声音、画面、转场之间的关系，不一定能靠分别生成文字描述再拼起来保留。分工有用，但不是所有东西都适合拆开。

## 用 Agent，为什么会想到买带鱼屏？

换一个话题，这次不用猜未来，看窗口就行。

Codex 里加入浏览器后，网页旁边还有聊天区和会话列表。如果原来的网页宽度不想缩小，新来的两块区域就需要额外空间。

于是，买更宽屏幕成了一个具体的使用念头。

这并不意味着 Agent 必须配带鱼屏。它说明的是，这种界面正在要求用户同时看几件事。普通比例的屏幕可以分，但每分一次，可用宽度也少一截。

那么，买了就解决了吗？

也没有。链接在侧栏还是独立窗口打开，最好能预先知道；同一任务的网页，最好能跟着项目组织。如果这些关系是乱的，更大的屏幕只会让更多窗口同时可见。

浏览器加 Agent，与 Agent 加浏览器，也因此不只是两个功能列表。一个从浏览开始，一个从任务开始。对后一种路线的乐观，是期待上下文能围绕任务聚拢，不是已经证明它一定赢。

## 屏幕加宽了，硬盘为什么又满了？

节目中的一段个人经历是：512 GB 不够用，换到 2 TB，约三个月又占了 1 TB。

不能把这全算成 AI 生成内容。依赖、工作副本、浏览器缓存、虚拟机、系统镜像、原始视频，都可能在里面。创作和开发做得越多，这些东西也越容易留下来。

换硬盘解决容量，备份解决另一类问题，冷存储又涉及取回的等待。便宜值得不值得，要看文件多久用一次、临时要用时能等多久。没有一种方案仅凭价格就适合所有文件。

## 功能变多，为什么还要用户先选模式？

ZCode 的 Coding 与 Office 模式，以及 Claude Code 的项目、会话、云端工作方式，都触到了同一个使用疑问：工具已经越来越会做事，用户是不是还得越来越会分类？

想完成一件任务，先决定它叫 Work 还是 Code，再理解项目和聊天的关系。这些概念对系统有意义，对用户却未必都是开始工作的必要条件。

一个值得尝试的方向是少让用户做这种预判：先说要完成什么，再由工具选择路径。内部可以复杂，入口不必把复杂程度照单全收。

## 做得更容易，就会有更多人看吗？

这是内容创作者绕不开的最后一问。

不会配乐、不会剪辑，过去足以让一个想法停下来。工具补上这些能力，是实在的机会。但产出的速度提高，并没有给观众增加时间。

作品能否被看见，表达能否成立，仍要靠内容和传播本身。

因此，制作完成后还有一个问题，不能交给导出按钮回答：这件作品，为什么值得别人花时间？
