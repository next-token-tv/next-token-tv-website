## 每篇正文的内容结构

| 内容 | 写作要求 |
| --- | --- |
| 定位 | 开头直接说明是什么、由谁提供、属于哪个产品层级；区分模型、助手、开发平台和编码 Agent。 |
| 用途 | 给出产品特有的实际任务或工作方式，避免所有页面重复“提高效率”。 |
| 使用与区别 | 给具体官方入口，解释必要的桌面／CLI／网页／API 区别；只写与用户决定有关的限制。 |
| 节目讨论 | 有直接原文证据时写简短摘要、发言人或转述关系及引用；没有证据则省略。 |
| 常见问题 | 通常 3–6 个相关问题，实际数量服从需求证据；H3 问题下直接短答，不折叠。 |
| 来源 | 列能支持核心事实的具体页面，正文关键主张也就近链接。 |

FAQ 在介绍和讨论之后、来源之前。Markdown 从 H2 开始，页面组件已生成 H1；H2 自动进入目录。正文不再手写基本信息表、更新日期卡片或最后的相关节目列表，这些由页面数据与共享组件提供。

品牌正文讲业务和产品关系，人物正文讲身份、经历、代表作品及有据可查的关系。品牌页的导航类别仍是“品牌”；公司性质在正文中准确表达。人物关系从 YAML 的 `relations` 派生，mentions 不能替代关系依据。

## FAQ 选题与回答

1. 按分配条目采集真实搜索需求线索。记录日期、种子词、语言、返回候选和来源；只填写实际使用的数据源。优先公开联想、相关问题或实际站点查询，有权限时使用搜索数据服务。
2. 排除同名歧义，如 Gemini 星座、Codex 古籍、DHH 缩写的其他含义；必要时补全品牌名或产品用途再采样。
3. 记录“采样词 → 搜索意图 → 采用问题 → 官方答案来源”的映射。语言翻译、编辑归纳和额外解释性问题分别标明，不将自选 SERP 查询当作热门证明。
4. 答案先回答问题，再补必要条件与具体链接。“去官网看”“可能变化”不能代替回答。下载指向官方入口，API Key 指向官方创建或入门页面，计费解释免费层／订阅／按量计费的区别。
5. 不编造搜索量、难度、曝光、CTR、命中率或 GEO 效果；缺失指标为 N/A。联想顺序不是热度排名。

可复用[样板口径](wiki-faq-keywords.md)及[六产品研究记录](research/wiki-faq-ai-products-2026-09-17.md)的记录格式，不能把旧采样自动算作新产品证据。每批研究文件放在 `docs/research/`，原始数据与事实说明分开；不要让产品正文展示采样过程、内部评分或编辑注意事项。

## 事实与引用

- 产品功能、入口、状态、价格及版本先查官方原始资料。重要历史事实可使用可靠报道；搜索结果摘要不能替代来源正文核验。
- 模型家族页面不照抄未经核验的型号别名。`announced`、`preview` 不写成普遍可用；缺少证据时不发布该主张。
- 不为充实内容加入精确价格、配额、性能排名或公司数字。确有必要且证据充分时写清日期、条件和来源。
- 不复制营销宣传为客观评测结论；不把流畅写作或节目提及当作官方背书。
- 研究记录只保留事实、证据、采用范围和未知项；正文不出现“本页不固定价格”“需要补资料”等编辑过程。

## 时间稳定性与表述口径

正文介绍应尽量由与阅读时间无关的内容构成，接近百科条目，而不是某一次核验的快照。

- 定位、层级、提供方、形态与持久的设计或使用方式写稳定事实；历史事件（发布、开售、改名、收购、版本推出）写明具体日期，按既成事实表述，不使用“最近”“刚刚”“本周”这类相对时间。
- 正文不以“核验日”“本次核验时”为基准描述世界状态；核验过程只存在于研究记录，不进入正文。示例：不写“发售状态以核验日（2026-09-17）的官方资料为准……截至核验日尚未开售”，改写为“官方新闻稿显示该产品于 2026 年 9 月 9 日发布，10 月 23 日起在 70 多个国家/地区发售”。
- 在售机型、现行价格、API 当前模型等时效状态不写成正文断言：优先链接官方实时页面交由读者查询；确有必要时用“截至 YYYY 年 M 月”锚定，保持最少数量，并优先放在 FAQ 答案中。
- “当前”“最新”可以用于指向实时官方页面的指针（如“当前费率见官方价格页”），不能用于断言状态本身（如“当前旗舰是 X”）。
- “尚未”“即将”“预计”必须依附具体日期或官方公告，不独立使用。
- FAQ 问题保留真实搜索问法（问题里的“现在”是需求线索），只按本节改写答案。
- 英文正文同一口径；日期写法保持各自语言惯例。

## 节目引用规则

先读 `src/content/imported/transcripts/` 中真实原文，再写摘要。准确核对节目编号、章节 ID、发言人、转述对象及语境；不要根据 mentions 或章节标题臆测发言内容。

- 完整讨论引用 `#chapter-...`，具体一段话优先使用实际生成的 `#quote-...`。
- 章节标题需使用原名，或不加引号概述主题；不能杜撰章节名称。
- 区分亲身体验、转述、期待和尚未发生的发布，不把当时的预测写成当前功能。
- 不伪造行号、播放时间或未经核验的发言时间戳。`turn-*` 不作为长期引用首选。
- 段落锚点由发言人和归一化原文生成；修改原文、发言人或重复段落顺序可能改变锚点，须重新核对引用。

英文正文允许链接中文原文，链接文字明确写 `Chinese transcript`。目前本地导入的两期逐字稿是中文，不生成不存在的 `/en/weekly/.../transcript` 链接。若以后有英文逐字稿，再引用真实存在的对应章节。

## 文件与双语契约

文件为 `src/content/prose/products/<id>.wiki.zh-Hans.md` 与 `<id>.wiki.en.md`；品牌、人物分别使用 `brands/`、`people/`。字段示例见[技术规范](wiki-technical-implementation-plan.md)。

- 中文与英文各自独立可读，标题、description 与各自正文对应。产品比较、FAQ 可以按语言需求调整，不要求逐句机械翻译。
- 内链使用现有实体 ID 和无尾斜杠 URL；英文站内实体链接使用 `/en/wiki/...`，中文逐字稿例外需明确标注。
- `updatedAt` 是正文编辑日期；不顺手刷新 YAML `lastVerifiedAt`。确实复核元数据事实并获该批任务范围允许时，才更新其来源和核验日期。
- 一种语言尚未完成时，保留其摘要页和现有语言互链，不伪造已翻译正文。
- 主理人详情使用单独模板，目前不自动渲染 Wiki 正文。为主理人扩写前先确认页面接入方案，不只新增一个不会显示的文件。

## Agent 任务交接

分配任务必须包含明确的实体 ID、语言与文件范围。建议使用以下任务约定：

> 为指定的现有产品 ID 补充 `zh-Hans`、`en` Wiki 正文，遵循三份 Wiki 方案与仓库规范。复用共享布局；读取实体 YAML 和节目原文；核验官方事实；采集并记录 FAQ 需求线索。仅编辑所分配正文及该批独立研究文件。说明来源不足或无法核验的条目，不填充虚构内容。交付文件清单、实际检查结果与剩余问题，保留其他工作区改动；提交、推送和部署按本次任务授权执行。

并行 Agent 不编辑同一正文或共同汇总文件；由整合者更新完成清单和运行全站检查。已有本地实现需要随任务一起可见，不能仅提供三个规划文件而假定目标检出已具备组件与 schema。

## 内容验收

- 实体 ID、分类和双语字段有效，正文不重复 H1。
- 问题与答案具体、有用，FAQ 映射能追溯到真实需求线索或明确的编辑补充。
- 产品事实有来源，节目观点有准确归属，章节和段落链接实际存在。
- 无无关警告、关键词堆砌、空模块、编辑过程或重复逐字稿。
- 中英文内链、标题、description、日期及渲染结果一致。
- 按[技术验收清单](wiki-technical-implementation-plan.md)完成适用检查。说明检查与未完成项，不能将构建成功写成事实审核或上线成功。
