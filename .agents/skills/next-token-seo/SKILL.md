# Next Token SEO

在 `next-token-tv-website` 仓库中使用。先读 [技术 SEO 约定](../../../docs/seo-technical.md)；该文档维护长期契约与证据口径，本技能提供任务入口，不保存某次审计的页数、分数或部署状态。

## 确认范围

确认当前 checkout、Git 状态与待查变更，保留已有工作。区分源码、当前构建和公开站点；仅当存在可核实的发布记录时标注生产 revision，不能从页面可访问推断具体提交。按请求选取相关路由和检查，不因局部修复而自动开展全部 SEO、内容和后台审计。

## 选择验证入口

- Sitemap、canonical、hreflang 或 Markdown 改动：阅读 [URL 约定](../../../docs/url-conventions.md)，核对本地与线上 URL 集合及实际响应。测试响应头使用 Worker；端口和构建必须对应本次目标。
- 博客日期、作者或发布状态：阅读 [Blog 契约](../../../docs/blog.md)，检查对应语言的元数据、可见署名、结构化数据和编辑说明是否一致。涉及正文编辑时使用仓库 `next-token-blog` 技能。
- 页面呈现：阅读 [设计规范](../../../docs/design-guidelines.md)，验证对比度、可访问名称与中英文布局。优先修复对应样式角色，避免改变整个品牌色来解决单个文本问题。
- 性能：按技术 SEO 约定区分冷启动、重复访问与真实用户数据。先定位请求或渲染瓶颈，再决定改动；网络波动未定位时保留不确定性。使用已有 [性能审计机制](../../../docs/site-maintenance.md#independent-mobile-performance)，不另建重复的状态账本。

## 完成条件

代码修复按影响范围运行已有测试和新鲜构建的 `check:release`；对未来容易回归的边界补必要断言。检查范围与未覆盖项写清，实际 Worker 响应不可由源文件配置推定。

交付说明当前事实、具体修复、验证结果和剩余限制。旧报告是带日期的快照，引用前复核易变项；将新的事实写入本次报告，不把暂时故障变成永久规则。提交、推送、部署及后台写入分别按用户授权执行，审计或修复本身不代表这些动作已获授权。
